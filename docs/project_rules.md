# Project Rules

This document records the durable data, modeling, and runtime contracts for the
Healthcare RCM Intelligence Platform. It is tool-neutral and applies to every
change made to the repository.

## 1. Project purpose

Healthcare RCM Intelligence is an end-to-end revenue-cycle analytics portfolio
project. It ingests official CMS synthetic Medicare claims into a PostgreSQL
warehouse, adds a clearly labeled simulated adjudication layer, computes RCM
KPIs, trains explainable machine-learning models, and serves results through a
FastAPI API and Streamlit dashboard.

Honest data provenance is the primary contract: no simulated value may be
presented as real.

## 2. Architecture and data decisions

| Decision | Contract |
|---|---|
| Claims source | CMS Synthetic Medicare Enrollment, FFS Claims & PDE using the modern ICD-10 schema, not DE-SynPUF |
| Code vintage | ICD-10-CM/PCS and HCPCS references matching the source period; do not mix ICD-9 references |
| Dashboard | Streamlit |
| Demo data | The populated demo uses the committed DuckDB bundle; hosted readiness also validates a schema-only PostgreSQL database as documented in `docs/hosted_deployment.md` |
| Dependencies | `uv`, `pyproject.toml`, and `uv.lock` |
| Python | Python 3.11+ with type hints on public functions |
| Warehouse | PostgreSQL 16 through Docker Compose for local use |
| ML stack | scikit-learn baselines, XGBoost advanced models, SHAP explanations, and isotonic calibration |
| Random seeds | `config/simulation.yaml` and `config/model.yaml`; do not hardcode them |

## 3. Data provenance rules

1. Every field in every curated table has one classification: `SOURCE` (from
   CMS files unmodified), `DERIVED` (computed from source fields), `REFERENCE`
   (from official public reference files), or `SIMULATED` (generated by this
   project).
2. Every simulated table and column name is prefixed `sim_`.
3. Changes to a table or column must update both
   `docs/provenance_register.md` and `docs/data_dictionary.md`.
4. Synthetic claims contain synthetic provider and facility identifiers. They
   do not join to real NPPES NPIs or hospital CCNs. Display enrichment uses a
   reproducible seeded assignment stratified by state and type; the crosswalk
   is itself `SIMULATED`.
5. Medicare FFS has one payer. The multi-payer dimension is simulated, so every
   payer-level output requires the simulated-data disclosure.
6. Raw CMS files are never modified or committed. Only download logic,
   manifests, and checksums belong in Git.
7. CPT descriptions are not included because they are AMA-licensed. Public
   HCPCS Level II descriptions are permitted. Denial taxonomy uses CARC codes
   only as category labels.

## 4. ML leakage rules

Model A predicts pre-submission denial risk. Its forbidden-column blacklist is
defined in `config/model.yaml` under `forbidden_features` and includes denial
outcomes and reasons, payment and adjustment fields, adjudication dates, appeal
fields, recovered amounts, post-submission workflow events, and the latent
simulation probability.

1. `tests/leakage/` must reject any forbidden column, or a derivative of one,
   entering a training matrix.
2. Historical rates must use prior-period or out-of-fold computation.
3. Time-dependent features require temporal, not random, splits.
4. Preprocessing is fit only on training folds.
5. Models consume the published feature contract rather than simulation
   internals.

## 5. Reproducibility and secrets

- Secrets belong in environment variables or untracked `.env` files. The
  committed `.env.example` documents supported variables.
- Generated datasets must be deterministic under their configured seeds.
- The committed DuckDB artifact must carry its source SHA, dirty-tree status,
  fingerprints, and dataset inventory.
- Raw or sensitive healthcare data must never be committed.

## 6. Engineering and user-interface rules

- `main` must pass the automated test suite.
- New or changed behavior requires focused tests.
- SQL identifiers use snake case, and published views document grain, sources,
  and provenance.
- Python uses Ruff, Pytest, and type hints on public APIs.
- Every dashboard page renders the synthetic-data banner.
- Simulated markers and disclosures must survive SQL, serialization, API, and
  dashboard presentation boundaries.

## 7. Acceptance expectations

- **Data:** checksums and manifests are recorded; schemas pass validation; row
  counts reconcile within documented tolerances.
- **Warehouse:** foreign-key integrity passes and views reconcile to controls.
- **Simulation:** identical seeds produce identical outputs; directional checks
  pass; assumptions are documented with cited benchmarks.
- **ML:** baseline and advanced results are compared; calibration and slice
  metrics are reported; leakage tests pass.
- **Application:** Docker Compose starts from a clean clone; API schemas validate;
  dashboard totals reconcile to control queries.
- **Documentation:** README, data dictionary, model card, assumptions, and
  deployment limitations remain current.
