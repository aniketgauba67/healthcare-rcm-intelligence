# Model Card — Healthcare RCM Intelligence Platform

**Models:** A (pre-submission denial risk), C (appeal success + Expected Net
Recovery work queue). *There is no Model B; the letters follow the project brief.*

**Owner:** ml-engineer · **Phase:** 4 · **Runs:** `make train`, `make train-appeal`

> ### Read this before any number below
> **Every outcome in this project is SIMULATED.** The claims are official CMS
> *synthetic* Medicare data (SOURCE); the denials, appeals, payments and workflow
> events layered on top are generated by this project's own simulation and are
> prefixed `sim_` wherever they appear (CLAUDE.md §3). No real patient, provider,
> payer or adjudication data exists anywhere in this repository. The multi-payer
> dimension is 100% simulated — Medicare FFS has one payer.
>
> So **no metric here is evidence that this model would work on real claims.**
> What it is evidence of is that the *pipeline* is correct: point-in-time
> features, temporal splits, a leakage guard with teeth, honest intervals, and a
> baseline the advanced model has to beat and doesn't. That is the claim being
> made, and it is the only one.

Every figure is copied from `models_artifacts/model_a/metrics.json` and
`models_artifacts/model_c/metrics.json`, written by the runs themselves. Nothing
here is typed by hand. Two consecutive full runs are byte-identical
(`tests/models/test_determinism.py`).

## 1. Model A — pre-submission denial risk

### Intended use

Score a claim **at the moment before submission** so a billing office can route
the riskiest claims to a pre-bill reviewer. It is a triage aid. It is not a
payment decision, not a clinical determination, and not a reason to hold a claim
without a human looking at it.

### Boundary

Everything the model sees must be knowable before the claim goes out. The
blacklist lives in `config/model.yaml` and is parsed structurally from
`docs/simulated_forbidden_columns.md` — the §4.5 firewall interface — with set
equality asserted in **both** directions, so a column the document names and the
config omits fails the build, and so does the reverse.

### Data and folds

| | |
|---|---|
| Claims | 20,867 |
| Features | 39 |
| Split | temporal quantile cut at **2021-12-28** (never random) |
| Train / test | 16,694 / 4,173 (20.0%) |
| Folds | FIT 13,356 → CALIBRATE 3,338 → TEST 4,173, in time order |
| Train / test base rate | 0.1294 / 0.1205 |
| Test range | 2021-12-29 → 2024-06-17 |

Holding out the last calendar year was rejected: 2023 holds ~3.4% of claims, so
that fold would be tiny and unrepresentative. The calibration fold is carved off
the **end** of the training window, so the isotonic calibrator sees neither the
estimator's fit rows nor anything from the test period.

### Results on the forward test fold (503 denials, base rate 0.1205)

| model | ROC-AUC | PR-AUC | Brier | $ top decile |
|---|---|---|---|---|
| base rate (constant) | 0.5000 | 0.1205 | 0.10608 | 20.4% |
| payer rule | 0.5921 | 0.1514 | 0.10489 | 8.7% |
| **logistic (champion)** | 0.6254 | 0.2210 | 0.10280 | 39.0% |
| xgboost | 0.6257 | 0.2078 | 0.10418 | 29.4% |
| logistic + isotonic | 0.6185 | 0.1972 | 0.10368 | 38.4% |
| xgboost + isotonic | 0.6256 | 0.1982 | 0.10593 | 28.5% |

**The advanced model does not beat the baseline, and that is the reported
result.** XGBoost − logistic ROC-AUC = **+0.0003 [−0.0173, +0.0183]** — an
interval an order of magnitude wider than the point, so it is reported as *no
difference*. Logistic wins PR-AUC outright. The champion was chosen on the
calibration fold, never on test.

This is not a failure to tune. There is **no hyperparameter search anywhere in
this repository**, and `config/model.yaml` records why: with an oracle ceiling
near 0.68 and ~500 test positives, a search would be selecting on differences
smaller than the bootstrap interval — buying a better number and a worse model.
The domain reason a tree adds nothing is specific and was established in Phase 2:
the flagship `auth_required × auth_missing` interaction is *definitionally*
absorbed (you cannot miss an authorization that was not required, so
`auth_missing` already equals the interaction and a linear model captures it
fully), and the one genuinely tree-only interaction, payer × service line, is
thin because the source DRG mix is skewed.

Against a baseline that is not a strawman, the model does earn its place:
logistic − payer rule ROC-AUC **+0.0333 [+0.0066, +0.0571]**, PR-AUC **+0.0695
[+0.0444, +0.0998]**. Both exclude zero.

### Where 0.625 sits, and why higher would be worse

`config/model.yaml: sanity_bounds` puts the oracle — scoring with the generator's
own latent probability — at ROC-AUC **0.68**, and roughly **a third of observed
denials carry no mechanism signal at all** (deliberate label noise). A model above
0.75 fails the run with `SuspiciousPerformanceError` and writes to
`metrics_SUSPICIOUS.json` for diagnosis. **A suspiciously good number here is a
bug to hunt, not a result to report.** Observed 0.6185 calibrated; verdict *within
the documented noise ceiling*. Landing where Phase 2 predicted is corroboration,
not luck.

### Calibration

Isotonic, fitted on the 3,338-row calibration fold. ECE **0.01964 → 0.01753**.
Platt reaches 0.01621 on this fold; both are reported rather than the better one
being quietly selected. Reliability curve:
`models_artifacts/model_a/calibration_curve.png`.

### Operating point

**The capacity-constrained point is the primary one.** A work queue is ranked
against finite analyst hours, not thresholded against a guess.

| | flagged | recall | precision |
|---|---|---|---|
| **capacity-constrained (top 10% by score)** | 9.6% | 20.9% | **26.3%** (2.2× base rate) |
| cost-optimal threshold | 60.1% | 73.2% | 14.7% |

Both cuts are chosen on the calibration fold and applied unchanged to test.

#### The cost matrix, and what decomposing it did

The first version asserted `prevented_denial_value_multiplier: 1.0`. That single
number quietly made two claims at once — that a review prevents the denial *with
certainty*, and that a denial costs the *full claim value* — and the second is
badly wrong, because denials are appealed and substantially overturned. It is now
two named factors, each a **DESIGN CHOICE** cited to a published benchmark, and
multiplied in exactly one place in the code:

| factor | value | anchor |
|---|---|---|
| P(prevented \| flagged and worked) | **0.50** | Change Healthcare Denials Index: ~86% of denials are "potentially avoidable" — a ceiling on what any pre-bill intervention could reach — and about **half** arise from front-end causes: registration/eligibility (~27%, the largest single cause), authorization, service-not-covered. Those are what a pre-submission review can see and act on. This is the **optimistic** end of honest: it equates "had a front-end cause" with "was caught and fixed in time". |
| share of claim value permanently lost | **0.25** | Same index: ~24% of avoidable denials are **not** recoverable. Premier Inc.'s 2024 survey points the same way, with a majority of contested denials ultimately overturned and paid. This is a **floor**, deliberately — it describes a shop that works its queue. MGMA and Change Healthcare both report 50–65% of denied claims are never reworked at all, where the permanent loss is far higher. Taking the floor keeps the threshold from being flattered by an assumption of institutional neglect. |
| product used | **0.125** | |

**Neither factor is derived from the simulation.** The generator's realized
overturn and rework rates sit behind the §4.5 firewall, and reading them to set a
business parameter would make the operating point a function of exactly what the
firewall exists to hide. Both were fixed *before* the resulting threshold was
computed.

**What fell out — reported as measured, not as hoped.** A claim is worth reviewing
when `multiplier × P(denial) × dollars_at_stake > review_cost`. On the calibration
fold, where the threshold is chosen, that is `25 / (0.1306 × 3,029.75)` =
**0.0632**; the same figure is 0.0543 on the test fold and 0.0785 across the whole
book, so the break-even sits near 0.05–0.08 however it is measured. The decomposed
0.125 is above all of them — by a factor of about two, where the old 1.0 was above
by a factor of sixteen. Flagged share fell from **98.4% to 60.1%** at 73.2%
recall. So the decomposition moved the answer a long way and *still* did not
produce a usable operating point.

The sensitivity sweep is the real argument, and it stays a first-class artifact
for that reason:

| multiplier | 0.025 | 0.055 | 0.075 | **0.125** | 0.25 | 0.5 | 1.0 |
|---|---|---|---|---|---|---|---|
| flagged share | 6.7% | 6.7% | 13.6% | **59.9%** | 86.3% | 98.4% | 98.4% |

The flagged share swings from 13.6% to 86.3% while the multiplier moves across a
range no published source can narrow. The cost-optimal threshold is therefore
dominated by an assumption nobody has measured on this book — which is why the
capacity point leads. A business parameter nobody measured is a guess, and the
sweep is the honest representation of a guess.

### Dollars at risk — and the instrument that decides whether it means anything

Denied dollars in this fold are heavy-tailed: the **ten largest denied claims hold
50.9%** of the $1,920,446 at risk. Two point estimates with overlapping intervals
cannot settle whether one ranking beats another, because both intervals move
together when a single large claim changes decile. The reported instrument is
therefore a **paired** bootstrap on the difference, over the same resamples:

| comparison | difference | 95% interval |
|---|---|---|
| champion − constant scorer | **+17.9%** | [+4.2%, +51.7%] |
| champion − payer rule | **+29.6%** | [+7.1%, +53.4%] |

Both exclude zero, so the champion **is** distinguishable from arbitrary ranking
on this metric. That is a change of conclusion: read unpaired, the champion's
38.4% [16.0%, 59.3%] *contains* the constant scorer's 20.4% and supports no such
claim. The width is still enormous and **the magnitude is not pinned down** — a
+4.2% floor and a +51.7% ceiling are different businesses. Do not quote a single
number from this row.

Note the payer rule captures only **8.7%**, *below* the 20.4% a constant score
gets: it concentrates on a payer whose denials are individually small. Ranking
well by count and ranking well by dollars are different problems.

### Slice metrics

Bootstrap CIs on every scorable slice AUC, with an explicit `beats_chance`
column, because slices are the smallest folds in the report and therefore the
numbers most likely to be read as findings when they are sampling noise. Volumes
are shown beside every rate, always.

**By payer:** MCD_MCO 0.6445 [0.5737, 0.7113] · COM_REGIONAL 0.6038 [0.5196,
0.6900] · COM_LARGE 0.5921 [0.5262, 0.6532] · MCR_ADV 0.5775 [0.5318, 0.6218] ·
**MCR_FFS 0.5507 [0.4968, 0.6031] — covers 0.5.** Traditional Medicare FFS is the
archetype the model reads worst, and it is the largest slice (1,726 claims).

**By service line:** only AFTERCARE_REHAB (0.6499 [0.6135, 0.6837]) and
MSK_SKIN_ENDO (0.6092 [0.5305, 0.6845]) clear chance; UNKNOWN, RESP_CIRC and
TRAUMA_HIV_OTHER cover 0.5, and six more are too thin to score at all.
Per-service-line denial ranking was flagged weak in Phase 2 (Spearman 0.59,
p=0.056 latent-vs-observed) against per-payer strong (0.90), and this reproduces
that independently.

**By value band:** every band clears chance, 0.5933–0.6575. The model is not only
finding cheap denials.

**By facility/provider:** **1,801 providers in the test fold, 1 scorable.**
Grouping is on the synthetic `prvdr_num`, never the crosswalked real CCN
(CLAUDE.md §3.4). This is the honest answer — per-provider AUC is not computable
at this volume, and a table of nulls would imply it nearly was.

### Explanations

SHAP on the tree model: global importance plus claim-level waterfalls, every
feature mapped to an analyst reason code and a concrete action, **no feature
unmapped**. Top drivers: `sim_payer_prior_denial_rate` (PAY-02),
`billed_charge_amt` (CHG-01), `sim_payer_id` (PAY-01), `sim_auth_missing`
(AUTH-01 — *"obtain prior authorization before submitting"*),
`sim_documentation_complete` (DOC-01).

**Expect SHAP to fail on about a third of denials.** That is not a defect in the
explanation: ~33% of observed denials in this data are pure label noise with no
mechanism behind them, by construction. An explanation of an unexplainable denial
would be a fabrication.

SHAP is published for **Model A only**. Model C has none, deliberately and for a
measured reason — see §2, "No SHAP is published for Model C".

## 2. Model C — appeal success and Expected Net Recovery

### Intended use

Rank the **denial worklist**: given a denial that has posted, estimate the chance
an appeal is overturned and what appealing is worth, so a team that can work a
fraction of its queue works the right fraction of it.

### Boundary — and why it is not Model A's

**The boundary is the denial, not the submission.** A denials analyst opening a
worklist can read the remittance advice, so *what* was denied, *how much*, under
which category and CARC group, and *when* the payer adjudicated are all
legitimately available here and forbidden to Model A. Everything Model A could see
remains available, because a fact known before submission is still known after the
denial.

Two calls define the edge of that widening, and both stand:

* **`sim_denial_driver_mechanism` stays forbidden even for Model C.** It sits next
  to the *permitted* denial category in the schema, which is exactly why it needs
  saying out loud. A category is a CARC group on a remittance advice a human can
  read; the driver mechanism is the generator's own statement of *why* the denial
  happened, appears on no remittance advice anyone has ever worked, and admitting
  it would invert the §4.5 firewall through a column name.
* **`sim_appeal_disputed_amount` stays out, with `sim_denied_amount` as the
  substitute.** The two are equal on all 967 level-1 appeals (a one-time manual
  check against live Postgres; maximum absolute difference 0.00 — the pipeline
  does not recompute it, see below). They coincide numerically; they do not
  coincide in time. The denied amount is on the remittance advice at triage; the
  disputed amount is a fact about an appeal nobody has filed yet.

  **The column is no longer read at all.** It was previously selected by
  `APPEAL_TARGET_QUERY` and dropped again a few lines after the join. That looks
  equivalent to never reading it and is not: the drop was one refactor away from
  disappearing while the read remained, leaving a forbidden column on the frame
  with nothing objecting. It is now excluded at the query
  (`src/features/extract.py`), the same ruling applied to `clm_utlztn_day_cnt`.
  A forbidden column must never be READ, because a boundary enforced by a later
  cleanup step is a boundary that can be removed by accident.

Every `sim_appeals` column is forbidden as a feature — including the two targets,
because a target is not a feature and this guard is the only thing between those
roles. The payment date goes too: a payment posting after an appeal *is* the
appeal's result. `tests/leakage/test_model_c_boundary.py` asserts, as a set
relation, that C's blacklist is A's minus exactly the configured post-denial
facts — so a column added to A's list is covered here automatically.

### The limitation that matters most: selection

The model is **fitted on the 967 denials somebody chose to appeal** and **applied
to all 2,663**. Those are not the same claims:

| denial category | denials | appealed | appeal rate |
|---|---|---|---|
| MEDICAL_NECESSITY | 517 | 246 | 47.6% |
| DUPLICATE_CLAIM | 51 | 5 | 9.8% |
| TIMELY_FILING | 12 | 0 | **0.0%** |

Appealed denials are also larger on average. So the model estimates
P(overturn | appealed) and is applied to claims that were passed over for reasons
it cannot see — and for TIMELY_FILING it has **no training support at all** while
still emitting a score. This is selection on the outcome's own decision and **it
cannot be fixed from this data**. It is measured
(`models_artifacts/model_c/appeal_selection.csv`) rather than assumed away.

### Folds and results

967 appealed denials over nine years → fit 619 / calibrate 155 / **test 193**, cut
at 2022-03-08, 86 overturned. **Every interval here is wide and the honest
headline is not an AUC.**

| model | ROC-AUC | PR-AUC | Brier |
|---|---|---|---|
| base rate | 0.5000 | 0.4456 | 0.24714 |
| denial-category rule | 0.5571 | 0.4793 | 0.25056 |
| logistic | 0.5197 | 0.4769 | 0.28173 |
| **xgboost (champion)** | 0.5611 | 0.4914 | 0.25408 |

xgboost − category rule = **−0.0356 [−0.1325, +0.0597]**. The model does not beat
a rule that needs no model. Isotonic on 155 rows moves ECE 0.0886 → 0.0768; the
reliability curve uses five bins rather than ten, because 193 rows over ten bins
is nineteen claims a point and that is a picture of sampling noise.

**No slice beats chance.** Every payer, service-line and denial-category interval
covers 0.5 — e.g. PRIOR_AUTH_MISSING 0.7188 [0.4815, 0.9091] on 18 claims, and
CODING_INVALID 0.3399 [0.2000, 0.5023] on 31. The point estimates are not
findings. 157 providers in the test fold, **0 scorable**.

**No SHAP is published for Model C. This is a deliberate omission, not an
oversight, and the reason is the measurement two paragraphs up.** SHAP *is*
delivered for Model A (§1, "Explanations"); the difference is what the two models
measured. Model C's paired interval against the denial-category rule is
**−0.0356 [−0.1325, +0.0597]** — it spans zero, so on this test fold the model is
not distinguishable from a rule that needs no model at all, and every slice
interval covers 0.5 besides. A model that cannot be separated from a lookup table
has nothing stable to attribute. Publishing per-claim waterfalls over it would
manufacture exactly the impression the numbers refuse to support: that the score
has identifiable drivers a reader can act on. Attribution is only honest once
there is a signal to attribute, and 193 test rows have not established one.

What an analyst gets instead is not nothing, and it is not a weaker substitute:
the explanation for a denial is the queue's **tier** and its
`recommended_action`, which are rule-based, auditable, and true by construction
rather than estimated. If a later refit on more appeal volume separates the model
from the category rule, SHAP for Model C becomes appropriate and should be added
then.

### The work queue

`Expected Net Recovery = P(overturn) × recoverable × recovery_ratio − processing cost`

The **score** ranks. The **queue** is not the score sorted descending, and the
difference is deliberate. Two things outrank money and are applied as explicit
**tiers**, never folded into the number as weights:

| tier | ordered within by |
|---|---|
| 0 `DEADLINE_CRITICAL` | days remaining, ascending |
| 1 `MANDATORY_REVIEW` | expected net recovery |
| 2 `VALUE` | expected net recovery |
| 3 `BELOW_COST` | expected net recovery |
| 4 `EXPIRED` | not appealable; do not work |

A weight can always be outvoted by a large enough dollar figure, silently, with no
way to see it happened — and the failure mode is a time-barred appeal the model
quietly ranked four hundredth. As tiers the guarantee is structural and testable,
and it is tested on the adversarial case directly: **$200 with three days left
outranks $500,000 with four months**, plus 50 randomised queues.

`BELOW_COST` claims stay in the queue rather than being dropped. "We decided not
to" and "it never appeared" are different answers when someone asks later why a
claim was written off.

**Assumptions.** `appeal_processing_cost_usd: 45.0` — MGMA benchmarks denied-claim
rework at ~$25–$118 and Premier's 2024 reporting puts roughly $44 per contested
claim; $45 is the appeal-specific figure. `sim_operating_costs` is a forbidden
table for both models, so this is a published benchmark and not a value read out
of the generator. `filing_window_days: 120` and the 14-day critical window follow
the Medicare Part A/B redetermination timetable. `mandatory_review_categories`
(medical necessity, eligibility/coverage, coordination of benefits) is a stated
**project policy**, not a claim about regulation: writing off a coverage or
coordination-of-benefits denial can push balance onto the beneficiary, and a
medical-necessity denial is a clinical determination that a dollar threshold
should not silently close. They are configured rather than hardcoded so the policy
can be argued with. The recovery ratio (**0.8156**) is measured on the fit fold
only; it is flat across category (0.74–0.83) and uncorrelated with claim size
(r=0.02), so a richer model of it would be fitting noise.

Processing cost is a constant subtracted from every claim, so it sets **which**
claims are worth working, not the **order** they are worked in.

### What the queue is worth — the comparison that decides it

Recovered dollars are observed only where an appeal was actually filed, so the
value comparison runs on appealed test rows. That restriction flatters every
ranking equally.

| rule | recovered dollars captured at 10% capacity |
|---|---|
| **`largest_denial_first`** | **65.7%** ($138,786 of $211,282) |
| `enr_score` | 61.0% |
| `enr_tiered_queue` (shipped) | 59.8% |
| random | 0.7% |

| paired difference (same resamples) | point | 95% interval |
|---|---|---|
| enr_score − largest_denial_first | −4.7% | [−16.7%, +0.9%] |
| enr_tiered_queue − largest_denial_first | −5.9% | [−28.1%, +8.5%] |
| enr_tiered_queue − enr_score | −1.2% | [−21.6%, +14.1%] |

**The probability does not earn its place.** Sorting by denied amount does at
least as well; the interval is almost entirely negative and only touches zero at
the top. On this data the honest recommendation is the **simpler rule**, and
Expected Net Recovery is worth shipping for the *cutoff* it provides — which
claims clear cost, and the tiering — rather than for the *ordering*.

The reason is visible in the arithmetic: the model's probabilities are nearly flat
(ROC 0.56), so `P × amount` is dominated by `amount` and the two rankings nearly
coincide. A stronger appeal model would separate them. This is also why the third
row matters: the policy tiers cost about 1.2 points of recovered dollars against
the unconstrained score, which is the price of not letting a big claim outvote an
expiring one — and the interval says even that is not measurable at this fold
size.

### Deadline pressure — because a rule nobody has seen fire is not a guarantee

Neither headline queue exercises the deadline tier, and that is a property of the
two conventions rather than of the rule:

* the **backtest** triages every claim on the day its denial posts, so every claim
  has the full 120-day window ahead of it and nothing is ever urgent — VALUE 207,
  MANDATORY_REVIEW 170, BELOW_COST 91, **DEADLINE_CRITICAL 0**;
* the **live snapshot** is one instant, and this warehouse's 2023–24 tail holds
  ~3% of claims, so on the last day (2024-07-10) **1 claim is open and 467 are out
  of window**. Arithmetically true, and not a work queue. It is reported with that
  caveat rather than quietly dropped, because it is the shape a dashboard would
  render.

So the queue is also rebuilt at each **month start** across the window, which is
how a worklist is actually read — a claim sits on it, ages, becomes urgent. Over
**22 monthly queues**: VALUE 718, MANDATORY_REVIEW 587, BELOW_COST 311,
**DEADLINE_CRITICAL 237**, with **237 distinct claims** reaching the urgent tier
and the ordering guarantee re-asserted on every snapshot rather than only on the
two headline queues.

## 3. Leakage controls

* **Forbidden-column blacklist** parsed structurally from the firewall document,
  set equality both ways, with a deliberate-drift test proving the check can fire.
* **Point-in-time feature store** built from **base tables with an explicit
  allowlist**, not from `vw_claim_enriched`. That view carries the label, the money
  and the latent probability, so selecting it wholesale would leave a drop-list as
  the only thing between them and the model. Every feature declares its source
  columns and the build refuses a frame that does not match the declaration — a
  name-based guard cannot tell `payer_prior_denial_rate` from `payer_denial_rate`,
  and only one of those is a feature.
* **Historical rates are prior-period with an embargo.** "Submitted before *t*" is
  not "known before *t*": a claim submitted last week has not come back from the
  payer. Model A uses **60 days** (a payer adjudication and posting cycle); Model C
  uses **180**, from the published Medicare redetermination timetable — 120 days to
  file plus 60 for the contractor's decision. Both come from business rules and are
  deliberately **not** fitted to observed adjudication or decision timing, which
  would mean designing a feature out of a forbidden column. Rates shrink toward the
  moving book rate; no history yields **null, never zero** — a zero would tell the
  model the first claims in the warehouse came from flawless providers.
* **Point-in-time safety is tested behaviourally**, not structurally: truncate at
  *t* and past features must be bit-identical; scramble every post-*t* label and the
  past must not move; flip a claim's own outcome and its own features must not move
  — with a **control test** asserting that a naive whole-dataset provider rate *does*
  break all three, so the checks are known to be sensitive.
* **The training matrix is discoverable, and the guard runs on it.** Before this
  was closed, `src/features/` held six modules and no matrix any discovery route
  could find, so the §4.1 *value* probes — the ones that catch a renamed, logged,
  binned, ratioed or aggregated forbidden column, which is the only kind a name
  check cannot catch — **skipped**, and a skip reads like a pass. The matrix is now
  exported to `artifacts/features/model_a_training_matrix.parquet` and **committed**,
  so the probes run on a clean clone with no warehouse and no environment
  variables. Strongest single-feature AUC **0.5859** (`sim_payer_id`) against the
  **0.6778** oracle ceiling.

### Two SOURCE columns worth naming

**`clm_utlztn_day_cnt` is FORBIDDEN.** Measured before classifying, because a
covered-day count that was only ever a fixed offset from the calendar stay would
carry no information and the call would be moot. It is not a fixed offset:
`length_of_stay_days` is `(discharge − admission) + 1` on 100% of 20,867 claims —
pure calendar arithmetic a biller can do at submission — while `clm_utlztn_day_cnt`
equals `(discharge − admission)` on 92.47% of claims and is one day *short* on the
other 7.53% (1,572 claims). That short-day cohort carries **7.2× the mean
non-covered charge** ($2,784 vs $385) and a higher rate of any non-covered charge
(47.2% vs 37.9%). The missing day is the payer declining to count a day as
covered — the same adjudication event `nch_ip_ncvrd_chrg_amt` records in dollars.
It was removed from the **extract query**, not merely from the spec, so it is never
read rather than read-then-dropped. `length_of_stay_days` stays permitted.

**The three excluded CMS adjudication outputs are not empirically load-bearing,
and this card will not imply otherwise.** `medicare_source_paid_amt`,
`ncvrd_charge_amt` and `bene_deductible_amt` are real CMS **SOURCE** columns,
excluded because a biller does not know any of them at the moment before
submission — the same test §4 applies to the simulated layer. Their measured
correlation with the label is **0.0477 / 0.0117 / 0.0008**, and `clm_pmt_amt`'s
0.0477 is *identical* to `billed_charge_amt`'s: both merely track claim size. That
is exactly what should be expected, because these are real Medicare outputs and
the label is simulated and independent of them.

So **no live leak was caught here.** The exclusion is load-bearing on the pipeline
being correct *as if the data were real*, which is the property this project exists
to demonstrate (CLAUDE.md §1). Stating it the other way round — implying a
dangerous leak was found and blocked — would be the exact kind of overclaim the
provenance rules are written to prevent.

## 4. Ethical and operational considerations

* **Protected attributes are excluded.** Beneficiary sex and race are available in
  the warehouse and are deliberately **not** features. Age is included: it is
  clinically meaningful in a Medicare population and largely carried by the DRG
  anyway. There is **no fairness audit by race or sex here, and there should not be
  a reassuring one** — the outcomes are simulated, so any disparity measured would
  be a property of the generator, not of a payer.
* **The crosswalk to real facilities and NPIs is display-only** and forbidden as a
  feature at every boundary, Model C included. It maps synthetic providers onto
  real CCNs by seeded random assignment purely so the dashboard has recognisable
  names; it carries no information about the claim and multiplexes 4,876 synthetic
  providers onto 2,857 real CCNs (worst case 8:1), so a real CCN is not even a
  stable entity key. All provider analysis keys on the synthetic `prvdr_num`.
* **Coverage is claim-weighted, not provider-weighted.** The median provider has
  two claims and never builds a usable history, but volume is concentrated — the
  top 10% of providers hold 53% of claims — so **72% of claims** (83% post-2019) do
  carry provider history. Those are different questions, and the claim-weighted one
  is the one that matters for a queue.
* **Do not use Model A to deny care or delay a claim without review.** It flags
  claims for a human; at the 26.3%-precision operating point roughly three in four
  flagged claims would not have been denied.
* **Model C's score must never silently drop a deadline-critical claim.** That is
  why urgency is a tier rather than a weight, and why the guarantee is asserted on
  every queue the run builds, not only on the ones that reach the report.

## 5. Known limitations

1. Every outcome is simulated. Nothing here transfers to real claims without
   refitting and revalidating.
2. Model A's ceiling is ~0.68 by construction, and ~33% of denials are
   unexplainable label noise.
3. Model C's test fold is 193 rows. No slice beats chance, and the queue
   comparison cannot separate the model from a size sort.
4. Model C trains on appealed denials and scores all denials (§2 above);
   TIMELY_FILING has zero training support and is still scored.
5. The cost-matrix factors are published benchmarks, not measurements on this
   book. The sweep shows how much rests on them.
6. Dollars-at-risk is measurable but not precise: the paired interval excludes
   zero and spans +4.2% to +51.7%.
7. One Model A run diverged from five others and has never been reproduced. The
   leading hypothesis was tested and **rejected** (§5.1 below). Cause remains
   unexplained; `tests/models/test_determinism.py` stands guard.
8. Model C's live snapshot is degenerate on this warehouse (1 open claim) because
   of the thin 2023–24 tail.

### 5.1 The unexplained run, and the hypothesis that did not survive

One Model A run on 2026-07-27 reported `xgboost − logistic` ROC-AUC **+0.0026**
where five other runs that day reported **+0.0003**, and uncalibrated ECE
**0.02056** against **0.01964**. It has not recurred.

The standing explanation was multi-threaded XGBoost: gradient histograms summed
in a thread-scheduling-dependent order, floating-point addition not being
associative, so identical inputs can yield slightly different splits — a known
library property that would produce exactly this signature (rare, tiny, not
reproducible on demand). `estimators.xgboost.n_jobs: 4` was the suspect.

**Tested on 2026-07-28, and it does not hold here.** Fitting the same XGBoost
pipeline on the same fit fold and hashing the raw test-fold scores gave **one
distinct hash across 38 fits** — 20 at `n_jobs=4` and 20 at `n_jobs=1` in one
process (identical to each other), plus 3 fits in each of six separate processes
at `OMP_NUM_THREADS` of 1, 2, 3, 4, 8 and 16. Every one:
`607f1d7abd126139`. XGBoost's `hist` tree method is bitwise deterministic on this
data regardless of thread count, so thread scheduling cannot be the mechanism.

Two further points argue against it independently. The figure that moved was
`ece_uncalibrated`, which belongs to the **champion — and the champion is
logistic**, not XGBoost; a defect confined to the tree model could not move it. A
champion *flip* would explain both numbers at once, but the selection margin on
the calibration fold is PR-AUC 0.2769 vs 0.2576, a gap far too wide for a
floating-point perturbation to cross.

**qa-reviewer reached the same conclusion independently**, on a separately
written probe: 8 fits at `n_jobs=4` and 8 at `n_jobs=1` gave one digest across
all 16, identical between thread counts. Two independent measurements, two
different harnesses, same answer. The likeliest remaining explanation is the
mundane one — that the diverging run was on a different tree mid-development,
with no RNG involved at all.

So the cause is genuinely unknown, and it is recorded that way rather than
attributed to a plausible mechanism that the measurement rejects. What limits the
consequences is that **the champion is logistic**, so no headline figure in this
card depends on the XGBoost path; the diverging quantity is a comparison against
a model that loses either way. `tests/models/test_determinism.py` fails the build
if two consecutive runs stop agreeing.

One real order-instability *was* found and fixed while testing this: the SHAP
global-importance table was sorted with pandas' default non-stable quicksort, so
the features XGBoost never split on — all tied at exactly 0.0 — could reorder for
reasons unrelated to the model. Both sorts now pass `kind="stable"`. That was
never the divergence above (importances are not inputs to any metric), but it was
making this artifact's diffs noisier than the underlying model.

### Artifacts carry their own provenance

Everything these runs write is designed to be honest **when read alone**, because
that is how artifacts are actually read — a CSV opened from a file browser, a PNG
pasted into a slide, long after this card is out of sight.

- Every saved figure carries the synthetic-data banner, applied by the single
  writer `_save_figure` in `src/models/train.py` — the only place in the project
  that calls `savefig`. A new plot gets the banner by construction, and one that
  bypasses the writer fails `tests/leakage/test_plot_provenance_banner.py`, which
  checks structurally (AST) that every figure-writing function also writes a
  banner.
- Each run writes a `README.md` into its artifact directory stating that every
  outcome is simulated, calling out `slice_payer.csv` (a payer-level analysis, and
  the payer dimension is 100% invented — CLAUDE.md §3.5) and `work_queue*.csv`
  (which read as operational worklists for denials that never happened).
- `metrics.json` embeds a `provenance` key and is valid JSON with no bare `NaN`
  tokens.

Seeds live in `config/model.yaml` (`seed: 1337`) and are never hardcoded.
